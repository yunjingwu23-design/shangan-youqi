# 身份、数据隔离与后续微信绑定

## 当前信任边界

`auth.users.id` 由 Supabase Auth 管理，`app_users.user_id` 是随机生成的独立内部 UUID。一个 Auth 用户唯一映射到一个内部用户，邮箱和昵称均不作为主键。`profiles`、四种 `workspace_entries` 和未来 `external_identities` 均通过内部 `user_id` 关联。

应用通过 HttpOnly Cookie 读取会话，调用 Supabase `getUser()` 校验真实用户，再使用该用户会话查询自己的映射。请求体不接受 `user_id`；读写显式附加服务器得到的所有者条件。管理员客户端不用于普通业务资料的查询/修改；除原子限流和已认证本人注销外，新增的私有录音签名/清理先校验会话与所有权。独立 Worker 的管理凭证只用于已领取任务和私有文件处理，不进入浏览器。

数据库 RLS 通过受限 security-definer 函数把 `auth.uid()` 映射到内部用户。`app_users` 仅允许本人读取，所有者映射不能由普通用户写入。资料仅允许修改白名单列，记录不可改 `user_id`/`kind`/时间戳；RLS 同时检查行的读取权限和写入后所有者。`private` schema 不对 PostgREST 暴露。security-definer 函数固定空 `search_path` 并使用显式 schema，权限按角色显式授予。

同源 Origin 校验、JSON 类型、请求体大小上限、Zod 字段白名单和 http(s) 链接白名单均在服务端执行。用户文字由 React 转义展示，没有富文本 HTML 注入或服务器抓取用户 URL。

当前退出仅清除当前设备的会话并撤销该会话 refresh token。已经签发的 access token 在其到期前可能仍有效（Supabase JWT 的正常边界），不能承诺普通退出瞬间撤销已被窃取的 token。注销账号则删除 Auth 用户和内部映射，旧 token 即使未过期也无法通过 RLS 找到业务所有者。

## 导航草稿与搜索

未保存的简历、个人资料、投递表单、练习/笔记、逐字稿/报告和运营表单按服务端验证的 Auth 用户 UUID 隔离，临时保存在当前标签页的 sessionStorage；只恢复 24 小时内的内容。它不是新的身份标识或认证凭据，不能绕过原有 user_id、版本校验或 RLS。退出、清空数据、注销及身份变化时清除暂存；浏览器禁用存储时仍可手动保存到服务端。

待上传文件仅在根布局的标签页内存保存，不转为 base64 写入浏览器存储；站内返回可恢复 File 对象，刷新/关闭时提示重新选择。录音授权复选框不会自动勾选。保存后的录音仍仅存在原 Supabase 私有桶。

全站搜索的公开岗位和指南允许匿名读取；个人记录只由已验证的用户会话按内部 user_id 查询。搜索结果不跨用户缓存，前端隐藏导航不构成权限边界。后台根布局及原岗位 API 都要求明确的 site_managers 身份，前台导航和页脚不暴露后台入口。

## 数据删除

- 删除个人数据：一个数据库事务内删除投递/简历草稿/收藏/面试复盘，并清空资料，保留邮箱账号和内部 ID。
- 注销账号：要求 10 分钟内的 OTP 认证记录（刷新 token 不延长此窗口），确认文本匹配，服务端只能删除当前真实 Auth 用户；外键级联删除内部用户、资料、记录和外部身份。
- 新增私有录音：删除面试、清空个人数据、注销账号会同时删除复盘元数据并尝试删除文件。数据库触发器保留仅含对象路径的清理账本，Worker 在签名上传凭证有效期后再次清理，防止在途上传复活文件。此清理依赖 Worker 常驻，不得只部署 Vercel 页面。
- 此处删除指在线业务数据；托管项目备份、邮件服务日志和法定保留记录的生命周期由对应服务及运营策略管理。

## 微信 OAuth 第二阶段（尚未实现）

登录按钮保持禁用并显示「即将开放」，无二维码和回调端点。`external_identities` 当前仅预留表和本人读取权限，浏览器没有写权限。不能通过提交 `openid`、昵称或邮箱直接绑定。

未来完成网站应用资质与微信开放平台审核后：

1. 已认证用户主动点击绑定；服务端校验近期重新认证，使用服务端会话生成绑定用途的一次性随机 state，设置短过期，并使用提供方支持的 PKCE/授权码保护。
2. 仅在固定 HTTPS 回调接收授权码；验证 state 的会话归属、绑定用途、有效期和单次消费，服务端向官方 token/身份端点兑换并验证结果。不得信任浏览器传来的 subject、邮箱、昵称或 unionid。
3. 身份唯一键为 `(provider, issuer, subject)`，其中 issuer 包含应用作用域，subject 使用官方验证后的 openid；只有官方返回且已验证时才考虑 unionid，不能假定其总存在。
4. 在事务内锁定当前内部用户和外部身份唯一键，拒绝绑定已属于其他内部用户的身份，发生冲突提示用户处理；禁止根据邮箱或未经验证的身份自动合并。
5. 绑定成功只新增身份关系，继续使用原来的 `app_users.user_id`，不迁移、不删除原有简历、投递或面试记录。
6. 将来微信登录只接受已验证的身份关系再建立本系统认可的 Supabase Auth 会话；单独插入一条 external_identities 记录不等于完成登录。此服务端桥接、解绑、恢复和防重放测试需随 OAuth 实现一起交付。

不启用一个会按相同邮箱自动合并账户的第三方 provider 来替代上述显式绑定流程。所有未来用户级表和 Storage 路径必须继续以内部 `user_id` 建立隔离及回归测试。
