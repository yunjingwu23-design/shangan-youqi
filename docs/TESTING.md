## 认证与真实数据场景

1. 未登录的个人资料/记录 API 返回 401，工作台导航跳转登录。
2. 非同源或缺失 Origin 的变更请求返回 403。
3. 新邮箱收到真实八位 SMTP 邮件；输入完整八位码后 Auth 验证通过，服务器设置 HttpOnly/SameSite=Lax Cookie；仅输入前六位会被拒绝。
4. 新用户自动有资料和独立内部 UUID；刷新不变，且与 Auth UUID 区分。
5. 错误码、已用验证码、超过有效期验证码被拒绝；过期场景在隔离本地库将发送时间调到 20 分钟前，仍由真实 Auth 判定。
6. 重复发送返回 429 和 Retry-After；连续猜测第 11 次被邮箱维度限流。
7. 个人资料及投递、简历、收藏、复盘四类内容真实写入 PostgreSQL，并通过独立数据库客户端读回。
8. 独立客户端用真实 refresh token 建立会话后读取同一内部 ID、资料和记录；另一次邮件 OTP 登录也保留 ID 和数据。为避免测试空等，后者仅在本地模拟发送冷却期已过；邮件仍由真实 SMTP 发出、验证码仍由 Auth 验证。
9. 本人可修改状态、编辑内容、删除记录，刷新页面仍保持最新数据。
10. 删除个人数据需要精确确认文本，清空 A 的四类内容与资料，同时保留 B 的投递和 A 的账号。
11. 退出后原浏览器 Cookie 清除，无会话 API 返回 401。
12. 重新创建四类记录后注销账号，确认 Auth 用户、内部映射、资料和四类记录均删除；旧 JWT 不再能读取私人业务数据。
13. 12 个并发限流 RPC 请求、配额 3，仅 3 个获准，验证跨实例所依赖的数据库原子性。

## 正式项目人工验收

完成 `CONFIGURATION.md` 的环境变量、迁移、SMTP 和两类 OTP 模板设置后：

1. 新浏览器输入邮箱 A → 收到验证码 → 完整输入邮件中的数字（支持 6–10 位）→ 自动进入空的私人工作台。
2. 创建投递记录，填写公司/岗位/备注 → 保存 → 刷新；编辑状态并再次刷新，数据保持。
3. 修改资料；在另一设备以同一邮箱重新登录，确认资料、记录和内部 ID 相同。
4. 邮箱 B 登录后看不到 A 的资料或记录。对开发/测试项目使用独立会话的 REST 验证上述权限矩阵。
5. 尝试错码、过期码、已使用码、连续重发和连续猜测，确认有可理解的错误/倒计时，不能进入工作台。
6. 退出后重新访问工作台需登录；已登录刷新/重新打开浏览器可恢复；保持会话直到 access token 到期后检查自动刷新（本轮没有等待一小时进行此人工长时验收）。
7. 创建两账号数据，在 A 清空个人数据后确认 B 保持；重新添加记录，然后在最近一次 OTP 登录 10 分钟内输入「注销账号」，确认 Auth 用户及业务数据已删除。
8. 检查微信入口为「即将开放」且禁用，没有伪造二维码。

正式环境仍需独立验收 SMTP 送达、托管项目权限、HTTPS Cookie/代理及线上部署，不能把本地结果代替公网验收。下方新增录音与 AI 复盘内部测试结果；微信 OAuth、智能简历解析、公开岗位与管理员模块不在本次实现范围。
